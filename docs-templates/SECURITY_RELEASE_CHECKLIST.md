# چک‌لیست امنیت قبل از انتشار

این سند با توسعه هر فیچر تکمیل می‌شود و مبنای تست امنیت پیش از انتشار عمومی است. وجود یک کنترل در کد یا قبولی تست عملکرد، به‌تنهایی به معنی تأیید امنیت نیست.

## روش استفاده

- برای هر فیچر جدید یا تغییر در ورود، دسترسی، فایل، API یا داده حساس، مورد مرتبط را به این سند اضافه یا به‌روز کنید.
- هر مورد باید تست قابل تکرار، نتیجه، تاریخ، نسخه/commit و مدرک بررسی داشته باشد.
- وضعیت‌ها: «نیازمند بررسی»، «در حال اصلاح»، «آماده تست»، «تأییدشده»، «ناموفق».
- فقط بعد از اجرای تست و ثبت مدرک، وضعیت را «تأییدشده» کنید. تغییر کنترل مربوطه، نیاز به تست مجدد دارد.
- نقص بحرانی یا پرخطر حل‌نشده مانع انتشار عمومی است. استثناها باید با دلیل، مسئول پذیرش ریسک و مهلت اصلاح ثبت شوند.
- تست‌های فشار، نفوذ و آپلود مخرب را در محیط آزمایشی مشابه production و با داده غیرواقعی اجرا کنید.

## ۱. فیچرهای پرخطر همین پروژه

**وضعیت: نیازمند بررسی**

هر فیچری که فایل می‌گیرد، لینک عمومی می‌سازد، پول جابه‌جا می‌کند یا داده حساس نشان می‌دهد، اینجا یک زیربخش جدا با مسیرهای کد، کنترل‌های موجود، فهرست تست و مدرک فعلی می‌گیرد.

## ۲. ورود، رمز عبور و نشست‌ها

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] ورود با رمز اشتباه، حساب غیرفعال و نقش نامعتبر رد شود؛ پیام خطا وجود حساب را افشا نکند.
- [ ] تلاش ورود و بازیابی/تغییر رمز محدود شوند؛ دور زدن محدودیت از طریق IP یا حساب‌های متعدد بررسی شود.
- [ ] رمز پیش‌فرض، حساب آزمایشی و رمز مشتق از کد ملی برای انتشار عمومی حذف یا با تغییر اجباری رمز جایگزین شوند.
- [ ] عمر نشست، خروج، تغییر رمز و غیرفعال شدن کاربر تست شوند؛ سیاست ابطال توکن‌های قبلی مشخص باشد.
- [ ] نگهداری توکن در مرورگر، خطر XSS و عملیات حساس بررسی شوند.

## ۳. دسترسی نقش‌ها و دستکاری شناسه‌ها

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] APIهای مدیر، مدرس و هنرجو با هر سه نقش و بدون ورود تست شوند؛ محدودیت فقط در رابط کاربری نباشد.
- [ ] با تغییر ID هنرجو، مدرس، کلاس، جلسه، فاکتور و پرداخت نتوان داده دیگران را خواند یا تغییر داد.
- [ ] عملیات حساس به مجوز فعلی کاربر وابسته باشد؛ حساب غیرفعال و توکن منقضی رد شوند.

## ۴. HTTPS، دامنه و پراکسی

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] گواهی معتبر، تمدید خودکار و انتقال HTTP به HTTPS روی دامنه واقعی تست شوند.
- [ ] API و QR با HTTPS و دامنه درست کار کنند؛ mixed content وجود نداشته باشد.
- [ ] ALLOWED_HOSTS، CORS و CSRF با دامنه‌های مشخص تنظیم شوند؛ origin و Host غیرمجاز رد شوند.
- [ ] هدرهای forwarded فقط از پراکسی مورد اعتماد پذیرفته شوند؛ دسترسی مستقیم اینترنت به بک‌اند بسته باشد.
- [ ] کوکی‌های امن، HSTS با دامنه و مدت مناسب، منع نمایش در iframe، nosniff و سیاست referrer بررسی شوند؛ CSP با رابط برنامه سازگار تست شود.

## ۵. تنظیمات production و اسرار

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] DEBUG=False باشد؛ خطای عمدی stack trace، مسیر فایل، متغیر محیطی یا اطلاعات دیتابیس را نمایش ندهد.
- [ ] SECRET_KEY و رمز دیتابیس/ذخیره‌سازی قوی و اختصاصی باشند؛ مقدار نمونه یا پیش‌فرض باقی نماند.
- [ ] اسرار در Git، image، فایل قابل دانلود، bundle مرورگر و لاگ‌ها نباشند؛ روش تعویض امن و ابطال دسترسی قبلی مشخص شود.
- [ ] `python manage.py check --deploy` اجرا و هشدارها با توجه به معماری استقرار رفع یا مستند شوند.

## ۶. اجرای سرویس‌ها و دسترسی شبکه

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] Django با Gunicorn یا سرویس production مناسب اجرا شود؛ runserver برای انتشار عمومی استفاده نشود.
- [ ] فقط ورودی وب لازم عمومی باشد؛ دیتابیس، Redis، پنل ذخیره‌سازی و پورت داخلی بک‌اند از اینترنت قابل دسترس نباشند.
- [ ] مجوز کاربر سرویس، فایل‌ها و containerها حداقلی باشد؛ برنامه به Docker socket یا اسرار سایر سرویس‌ها دسترسی نداشته باشد.
- [ ] timeout، محدودیت منابع و رفتار قطع/راه‌اندازی مجدد زیر بار تست شوند.

## ۷. ورودی‌های API و مرورگر

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] طول، نوع و محدوده ورودی‌ها کنترل شوند؛ فیلد غیرمجاز نتوان نقش، مالکیت یا مبلغ را تغییر دهد.
- [ ] XSS ذخیره‌شده و بازتابی در نام، نشانی، توضیحات و گزارش‌ها آزمایش شود.
- [ ] SQL injection، path traversal، SSRF و URL/redirect غیرمجاز در مسیرهای مرتبط تست شوند.
- [ ] متد غیرمجاز، بدنه نامعتبر و درخواست تکراری، خطای کنترل‌شده بدهند و داده را خراب نکنند.

## ۸. پرداخت‌ها و سوابق مالی

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] مبلغ منفی/نامعتبر، پرداخت بیش از مانده و تغییر شناسه فاکتور رد شوند.
- [ ] درخواست تکراری و هم‌زمان باعث پرداخت مضاعف، مانده نادرست یا ثبت ناقص نشود.
- [ ] تغییرات حساس با عامل، زمان و شناسه رکورد ثبت شوند؛ کاربر بدون مجوز نتوان سابقه را حذف یا تغییر دهد.

## ۹. حریم خصوصی، لاگ و بازیابی

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] رمز، توکن، تصویر، کد ملی و داده مالی غیرضروری در لاگ و گزارش خطا ذخیره نشوند.
- [ ] دسترسی به لاگ، فایل و backup محدود باشد؛ نگهداری و حذف داده‌ها طبق سیاست مشخص انجام شود.
- [ ] backup دیتابیس و عکس‌ها تهیه و بازیابی واقعی در محیط جدا تست شود؛ زمان و نتیجه ثبت شوند.
- [ ] خطاهای احراز هویت، عبور از محدودیت و تغییر حساس قابل پایش باشند؛ واکنش به رخداد و ابطال دسترسی مستند شود.

## ۱۰. وابستگی‌ها و بررسی نهایی انتشار

**وضعیت: نیازمند بررسی — اولویت بالا**

- [ ] وابستگی‌های Python، Node و imageهای Docker برای آسیب‌پذیری شناخته‌شده بررسی شوند؛ نسخه اصلاح‌شده همراه تست سازگاری اعمال شود.
- [ ] اسکن اسرار، تست‌های امنیت API و تست مرورگر در فرایند انتشار اجرا شوند.
- [ ] پیش از انتشار عمومی، بررسی امنیت مستقل متناسب با ریسک انجام و یافته‌های بحرانی/پرخطر رفع و دوباره تست شوند.
- [ ] گزارش نهایی به نسخه مشخص متصل باشد؛ تست‌های قدیمی به‌عنوان تأیید نسخه جدید استفاده نشوند.

## افزودن فیچر جدید

برای هر فیچر، این اطلاعات ثبت شود: نام و مسیرها، داده حساس، نقش‌های مجاز، ورودی‌های قابل کنترل کاربر، خطرهای محتمل، کنترل مورد نیاز، تست مثبت/منفی و هم‌زمانی، مسئول و مدرک نتیجه. اگر فیچر به یکی از بخش‌های بالا مربوط است، همان بخش را تکمیل کنید؛ در غیر این صورت بخش تازه‌ای بسازید.
